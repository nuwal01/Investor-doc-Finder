# Investor Doc Finder (IDF) — Context & Decisions

## 1. What this is

IDF is an AI agent that locates and returns **verified** annual report PDFs for companies globally, given a natural-language query (e.g. "ASML Holding 2023 annual report"). It is not a document search engine — it's a **verification pipeline with search attached**. The deliverable is not "a PDF that looks plausible" but "a PDF confirmed to be the correct company, correct year, correct filing type."

Current state: all seven original build phases complete, plus a shipped **HTML/JS web frontend** (`frontend/` + FastAPI `api.py`) that is now the **primary UI** — `streamlit_app.py` is retained only as a debug tool (see §3, §5). System is past initial build, in active debugging + product build-out. Batch pass rate: 11/15 on the standard test set. **Version control was established 2026-07-12 (`git init`, baseline commit `66e60cd`); as of `db66f4f` the tree has seven committed correctness fixes, four product commits (in-memory EDGAR→PDF, HTML/JS frontend + PDF-download endpoint, SSE live progress, per-session search history), and three docs/housekeeping commits — see §12 for the per-commit record and current residual risks.**

## 2. Core design principle

**Verification is the product. Search quality is secondary.**

`verify.py` is the correctness gate. A candidate document is only returned if it passes verification against company identity, fiscal year, and document type. Search engines (Exa, Tavily, EDGAR) are candidate generators, not sources of truth. This has one hard consequence that shapes every other decision below:

**`give_up` is a valid, designed outcome — not a failure to engineer around.** If no candidate passes verification, the system should say so rather than return an unverified best-guess. This principle was tested against real pressure (the temptation to relax verification or bypass access controls just to produce an answer) and held. Any future fix that trades verification confidence for a higher hit rate is a regression, not an improvement, unless explicitly re-decided.

## 3. Pipeline / runtime flow

1. **Intent parsing** (`intent.py`) — parse user query into company, fiscal year, and (where determinable) jurisdiction/listing signals.
2. **Resolver** (`resolver.py`) — raw CSV ticker lookup **always runs before** LLM-based parsing. Deterministic lookup is cheaper, faster, and unambiguous where it hits; LLM parsing is the fallback, not the default path.
3. **Source routing**:
   - US-listed → EDGAR spine (`edgar.py`) — structured, authoritative, no search engine needed.
   - India-listed → India-specific sources (`aggregators.py`).
   - Everyone else → Exa search first, Tavily as fallback (`web_search.py`).
   - UK-listed issuers get a scoped secondary Exa query targeting third-party mirror domains (annualreports.com, etc.) as a resilience measure — see §6, Fix 4.
4. **Verification** (`verify.py`) — independently confirms each candidate: is it a PDF, does it match company + fiscal year, what form type is it (10-K / 20-F / 40-F). This is a **separate check from whatever search step found the URL** — a search engine finding a document does not mean IDF has verified it.
5. **Caching** — verified results are cached to avoid repeat search/LLM cost on repeat queries.
6. **Result/give-up** — return verified result with metadata (source, form type), or explicitly give up with a reason.
7. **UI** — two frontends. The **shipped product** is a static HTML/JS app (`frontend/index.html`, `app.js`, `styles.css`) served by and talking to **FastAPI** (`api.py`): it runs searches (`POST /search`, or `GET /search/stream` for live SSE step-by-step progress), serves the verified document as a real PDF download (`GET /download`), and lists per-session search history (`GET /history`). `streamlit_app.py` is **retained only as a debug/inspection tool**, no longer the primary UI; it shares the PDF-resolution logic with the frontend via `pdf_delivery.py`.

## 4. Ambiguities that could cause silent wrong answers, and how they're handled

This is the most important section for anyone picking up this project. The most dangerous failure mode is not an exception — it's a **confident, wrong answer with no error raised**.

- **LLM fallback chain misparse → confident wrong-company answer (AMBIPAR case — wrong-company output CONFIRMED by a fresh live trace 2026-07-06; original mechanism partly wrong).** No *original* log survived (no log files in the repo); the stale `batch_results.json` showed one run resolving to `"Ambipar"` and failing on `"Wall-clock timeout (56s > 45s)"` — which is why "just a timeout" looked plausible. But a fresh live re-run (Gemini 503 → OpenAI 429 quota → **Groq**) reproduced a genuine wrong-company output, and it is worse and more specific than the original "Groq hallucinated a company name" framing:
    1. **Groq misparse.** Groq parsed `"AMBIPAR"` (a Brazilian environmental-services company) into `company_name="Ambiphar Limited"`, `country="IN"`, `ticker_or_id="MBAPL"` — a scrambled, hallucinated Indian ticker.
    2. **Resolver override AMPLIFIED the error.** `resolver.py._raw_token_override` is meant to guard against LLM ticker rewrites, but here the hallucinated token `MBAPL` exactly matched a `company_map.csv` row (`MBAPL,MBAPL,IN,,,MBAPL,5881`) and locked the pipeline onto a real but unrelated Indian company (StockDiscovery id 5881, Madhya Bharat Agro Products Ltd). That CSV row was almost certainly written by `resolver._cache_sd_id` during an *earlier* misparse run — so the hallucination is **persisted in the data layer** and now reproduces deterministically whenever Groq emits ticker "MBAPL". The guard did not catch the hallucination; it hard-wired it.
    3. **verify.py passed it.** The aggregators source builds StockDiscovery URLs with `skip_company_check=True`, so verify.py took its lenient trusted-source path; MBAPL's *genuine* annual report legitimately contains "mbapl" and matched FY2022-23, so it passed cleanly. The result returned `ok=true` with the wrong company's real annual report.
  So the corrected status: a wrong-company silent-success **is** real and now reproduced. But the root cause is **not** "no plausibility check on Groq output" alone — it is (a) Groq misparse, (b) resolver override amplifying it off a self-poisoned CSV cache row, and (c) verify.py's trusted-source path being unable to catch a resolver-level company mismatch. Also: **there is no plausibility/hallucination guard in `intent.py`** (verified by inspection — only JSON-parse recovery, defaults normalisation, and a regex fallback; none check the LLM's company output). The claim that such a guard "was written for intent.py" is false.

  **FIXED 2026-07-06 (two scoped passes, addressing (b) and (c); `intent.py` left untouched):**
    - **(b) Poisoned data quarantined.** The `MBAPL,MBAPL,IN,,,MBAPL,5881` row was moved out of `company_map.csv` into `data/company_map_quarantined.csv` (with an audit note). This removes the deterministic `_raw_token_override` hit. *Not sufficient alone* — the resolver's live `_scrape_stock_discovery` path could re-derive a similar row, which is why (c) is the real fix.
    - **(c) verify.py trusted-source identity check.** The `skip_company_check=True` path no longer skips company identity: it now requires the document to name both the resolved company (`company_name`) **and** the originally-requested company (`raw_company`), the latter enforced only when the two diverge (share no distinctive token). A resolver override to a different-but-real company (whose own report self-matches) is now caught. Validated offline (`_check_text` unit cases), **live on the real aggregators→verify pipeline** (StockDiscovery id 5881: an AMBIPAR-divergent request `give_up`s loudly, a matching request passes), and in the full batch (12/15; AMBIPAR now `give_up`s with a wall-clock timeout, no MBAPL).
    - **(c continued) Non-trusted path — now also covered (2026-07-07).** The same `raw_company`-divergence gate was extended to the non-trusted branch of `_check_text` (edgar / web_search / company_site), so a resolver override to a wrong-but-real company is caught there too, not just on the trusted path. Shared `_distinctive_tokens()` helper, same divergence condition (fires only when resolved/requested share no distinctive token; a no-op for normal resolutions). Validated: offline `_check_text` cases + **live on the edgar path** (a query overridden to Apple's real 10-K while requesting AMBIPAR → `give_up`) and **live web_search** (resolved=Sasol, requested=AMBIPAR → all candidates rejected, `give_up`), with ASML/R R Kabel confirming no regression. The wrong-but-real-company failure mode is now closed across **both** trusted and non-trusted verification paths.
    - **Residual (still open, by design):** the upstream LLM misparse itself (`intent.py`/`resolver.py`) is unaddressed — the fix is a verification-layer safety net, not a parse fix.
- **Cache schema drift.** When new fields are added to the result payload (e.g. `form_type`), old cache rows won't have them. The read path must treat missing fields as "not available," never as a false negative or a stale/wrong value. Flagged during Fix 3; not yet explicitly tested.
- **URL validity ≠ document validity.** A URL returned by a search provider (Exa) may carry a time-limited, session/fingerprint-bound access artifact — confirmed concretely in the Tullow Oil case, where a working URL from Exa's playground carried a Cloudflare clearance token (`cf_chl_f_tk=...`) in its query string. That token was issued to Exa's own request context; there is no guarantee IDF's independent fetch (different process, different session, possibly after the token expires) is treated as pre-cleared by Cloudflare. **Never treat "a search provider returned this URL" as equivalent to "IDF can reliably re-fetch or re-serve this exact URL."** Caching such a URL as a stable answer is the same failure class as the AMBIPAR hallucination: it looks correct today and silently stops working later.
- **Form-type/document-type conflation.** Different documents for the same company/year (e.g. a preliminary results announcement vs. the full annual report PDF) can have similar filenames and both be "real." Filename similarity is not evidence of correctness; verification must check content.

## 5. Finalized tech stack, with reasoning

| Choice | Reasoning |
|---|---|
| **LangGraph** over CrewAI | Explicit node/edge control over agent flow, suited to a pipeline with hard verification gates and designed give-up states, rather than a role-based multi-agent framework. |
| **Single swappable LLM wrapper** (Gemini default, OpenAI/Groq fallback) | One interface to maintain; provider swap is a config change, not a rewrite. Fallback exists for quota resilience — but this chain has a known validation gap (§4). |
| **Raw CSV ticker lookup before LLM parsing** (`resolver.py`) | Deterministic and free where it hits; LLM parsing is reserved for cases the lookup can't resolve. Cheaper and more reliable than LLM-first. |
| **EDGAR as spine for US filings** | Structured, authoritative, official source — no search-engine guessing needed for the segment it covers. |
| **Exa (primary) / Tavily (fallback) for non-US/non-IN search** | Exa is a **candidate-discovery and text-based verification aid**, not a fetch-and-deliver source. Confirmed against Exa's own API documentation (`/contents` endpoint, checked July 2026): it returns extracted content formatted as markdown and query-relevant highlights — extractive text, not raw file bytes. An architecture where "Exa fetches the PDF and hands it to IDF" was proposed and explicitly rejected once this was checked — see §7. |
| **verify.py as independent gate** | Deliberately separate from search/discovery so a search engine being fooled, or serving stale/inaccessible content, doesn't propagate into a "verified" result. |
| **HTML/JS frontend + FastAPI (`api.py`)** — the shipped UI | Static `frontend/` (no build step) over a thin FastAPI backend. Real PDF downloads (`/download`), live step progress over SSE (`/search/stream`), per-session history (`/history`). Design tokens live in `DESIGN.md`. |
| **Streamlit (`streamlit_app.py`) — debug tool only** | Kept for quick local inspection of the pipeline; **not** the primary UI. Shares PDF resolution with the frontend via `pdf_delivery.py`. |

## 6. Specific test cases and examples that drove decisions

- **ASML Holding 2023 annual report** — canonical test case for form-type detection (expected: 20-F). Drove Fix 3 (form type on result card).
- **AMBIPAR** — wrong-company silent success **confirmed by a fresh live trace (2026-07-06)**; see §4 for the full mechanism. Summary: under quota exhaustion the chain fell to Groq, which misparsed "AMBIPAR" (Brazilian) into "Ambiphar Limited"/country=IN/ticker="MBAPL"; `resolver._raw_token_override` matched the hallucinated ticker to a self-poisoned `company_map.csv` row and locked onto an unrelated Indian company (Madhya Bharat Agro Products Ltd, StockDiscovery id 5881); verify.py's trusted-source path (`skip_company_check=True` on aggregator URLs) passed that company's genuine annual report. Result: `ok=true`, wrong company, ~58s. The stale `batch_results.json` (older run: resolved "Ambipar", wall-clock timeout) is a *different*, non-deterministic outcome of the same query — behaviour varies with which LLM in the chain answers. The "hallucination guard in `intent.py`" this case supposedly drove **does not exist**; and `resolver._raw_token_override` amplified rather than caught the error here.
- **Tullow Oil plc** — initially diagnosed as an HTTP 403 UA block; closer inspection of the working URL obtained via Exa's own playground showed a `cf_chl_f_tk=...` query parameter — a **Cloudflare JS-challenge clearance token**, not a UA-blocklist issue. This is why the initial fix hypothesis (swap verify.py's User-Agent to a browser string) was rejected: it wouldn't mechanically work against a JS challenge, and deliberately bypassing a bot-block conflicts with the give_up principle. Fix 4's shipped solution — a scoped Exa query against third-party mirror domains for UK-listed issuers — passed live for this case by sidestepping the Cloudflare origin entirely, not by solving the underlying block. Direct-fetch from Cloudflare-challenged issuer sites remains an accepted `give_up` case.
- **Silknet JSC** — minimal English-language web presence; no shipped fix, flagged as a hard case for the search layer generally.
- **Aeromexico** — post-bankruptcy fragmented filing history; no shipped fix.

## 7. Rejected approaches, and why (do not relitigate without new evidence)

- **verify.py User-Agent spoofing to bypass Tullow's 403** — rejected. Root cause is a Cloudflare JS challenge, not a UA blocklist; a UA swap doesn't mechanically address that, and it would constitute evasion of a deliberate access control, conflicting with the project's own give_up principle.
- **Headless browser (Playwright) for Cloudflare-challenged domains** — deferred, not rejected outright. Adding per-request browser-automation cost is bad sequencing while the Fix 2 latency regression (~3s → ~60s per query) is unresolved. Revisit only after that regression is fixed.
- **Paid anti-bot/CF-bypass scraping API** — rejected on the same principle as the UA-spoof idea: same evasion, outsourced and monetized. Also adds a fourth external vendor dependency to a stack that hasn't stabilized its existing three-LLM/two-search-provider footprint.
- **"Exa as primary search + fetch, IDF just displays the result, fallback tool only if Exa fails"** — rejected. Checked against Exa's actual API documentation: `/contents` returns extracted markdown text and highlights, not raw PDF bytes or fetched files. There is nothing for IDF to "receive" from Exa beyond a URL and extracted text — the same inputs available today. This architecture would also demote EDGAR (a deterministic, authoritative source) below a probabilistic search API for cases EDGAR already handles well, which is a regression. **What Exa's extracted text *can* legitimately be used for:** supporting verification (confirming company/year/form-type match) without requiring IDF's own independent re-fetch of a possibly Cloudflare-gated URL. This is a real, scoped opportunity — see Build Spec, open item — but it does not solve final delivery of a working download link for Cloudflare-challenged origins.

## 7a. Result-display decision: multiple verified candidates, not a raw link list

A proposal surfaced to make IDF behave like the Exa playground directly: show every URL Exa returns, let the user open and judge them manually. **Rejected.** This would eliminate the one thing IDF does that raw search doesn't — verification. A list of unverified candidates (e.g., the actual annual report, a Fact Book, a full-year-results press release, and a sustainability mirror — all real documents, only one the right answer) handed to the user with no distinction is the same silent-wrong-answer risk as AMBIPAR, just relocated from the LLM to the human. It also makes `give_up` meaningless, since every query would "succeed" with a list.

**Decision:** when more than one candidate legitimately passes verification for the same query (e.g., ambiguous fiscal year boundary, or a company with both a standard annual report and a separate ESEF/XBRL filing that both pass), IDF shows multiple results — but only ones that passed `verify.py`, each labeled with what was actually confirmed (form type, matched fiscal year, source). The user chooses between checked options, not between a real report and a decoy. `give_up` still fires if zero candidates pass; the gate is never bypassed to populate a list.

## 11. Guardrails (process rules — apply to how work gets done, not just what gets built)

- **One file per change, per Claude Code prompt.** Established from prior experience with untraceable regressions from batched changes. Holds even under time pressure.
- **Root cause before fix.** Symptom-level fixes are not accepted without understanding the underlying mechanism. (E.g., Tullow's "403" was initially treated as a UA problem; only inspecting the actual URL structure revealed a Cloudflare JS challenge — fixing at the wrong layer would have shipped and silently failed.)
- **Scope creep gets flagged, not silently absorbed.** If a fix requires touching a file outside its stated scope (e.g. Fix 3 needing `cache.py`), that must be called out explicitly, with the reason.
- **New architecture claims must be verified against actual documentation/behavior, not inferred from a demo or playground UI.** (E.g., "Exa returns the PDF" was an unverified assumption based on playground output; checking Exa's actual API docs showed it returns extracted text/highlights, not files. This claim is now closed — do not reopen without new evidence from Exa's docs or support.)
- **Batch testing (15-company set) is the system-level validation gate** for any change before it's considered done — a single test case passing is necessary but not sufficient.
